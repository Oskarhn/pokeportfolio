## 3. What merging to `main` would do

(Traced from `.github/workflows/ci.yml`; full table in the release-sequence document §1.)

- A push to `main` runs `build-and-test`, `db-tests`, `native-checks`.
- `deploy-production` becomes eligible after `build-and-test` + `db-tests` (not `native-checks`).
- It reads `PRODUCTION_SUPABASE_URL`, `PRODUCTION_SUPABASE_PUBLISHABLE_KEY`, `CLOUDFLARE_*`. The two `PRODUCTION_SUPABASE_*`
  secrets **do not exist today**, so it would stop at its first guard (fail closed, nothing uploaded).
- CI **never** applies migrations and **never** deploys Edge Functions. A successful deploy would ship only the new web bundle.
- Not verifiable here: whether Cloudflare Pages' own Git integration still auto-deploys `main` (P163 asked the owner to turn
  it off). If it does, the merge alone ships the web bundle.

Why this blocks the merge: once the owner creates the two secrets (a release prerequisite), a merge ships the new web client
against a hosted database still at 104 migrations and hosted functions without `delete-account`, in whatever order the
merge happens to land, and nothing in CI enforces "migrations → functions → client". The measured cost of that mismatch
(§5, new frontend + DB104) is bounded and fails closed — deletion is unavailable, four DB-version-specific specs fail — but
it is exactly the half-rolled-out state the release sequence exists to avoid. The deploy gate was **not** weakened;
the prerequisite order is in the sequence document. `MERGE_BLOCKED_BY_DEPLOY_COUPLING=yes` ends when the owner has done
sequence steps 2–8 and 9–13 are scheduled together with the merge, or when the deploy job is made to refuse unless the
hosted migration count and function set match (not done here; a change to the gate needs its own decision).

Consequences: the old web client is safe against the migrated database (rollback of the web alone stays possible); the
new web client degrades gracefully against 104 but is not the intended long-lived state. DB-level ledger gate: 16 tests
(direct writes refused, all ten writers and the official RPCs still succeed, other users' rows untouched).

Account deletion release coupling: with **no registry configured** the function answers 503 `deletion_unavailable` **before**
any state change (verified in `_shared/account-deletion.ts` step 4b and by the p189 suites). With a registry configured but
**unreachable** the account is left *pending* (writes refused, data intact, retryable, operator `abort_account_deletion`)
— so the registry must be proven reachable before enabling (sequence step 4). With the migrations but no function, nothing
can call purge. Fail-closed throughout.
